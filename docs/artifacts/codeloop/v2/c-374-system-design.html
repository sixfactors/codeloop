Codeloop v2: the server, the lead agent and the task agents

c-374 · codeloop · v2 · system design

Codeloop is a work context engine for AI coding agents: it keeps what a team is building, what it has decided, what agents may do and what has been proven, next to the code, and hands each agent the part it needs for the step it is on.

Status: proposal, 20 October 2026, written from the approved v2 plan for the owner's review. No product code changes with this document.

What Codeloop is

Code context engines such as Augment, Sourcegraph and Serena help an agent understand the code: where things are and how they connect. That is necessary, and it is not enough for a team to trust an agent with real work. An agent also needs to know what is being built and why, what the team has already decided, what it is allowed to do and must never do, who has to approve what, and what has already been proven to work.

Today this lives in people's heads, chat threads, tickets and stale documents. Agents never see it, so they guess, repeat questions, skip approvals and redo work. Codeloop keeps all of it in one place, next to the code. It hands each agent exactly the part it needs for the step it is on, and it updates itself as work happens. It reads the code too, and its job is the context around the work. That makes it a context engine plus a lightweight work system: it holds the context, and it records what happened.

Teams trying AI coding tools on existing systems report five problems: the tools do not understand the existing system; there is too much process for small changes and too little for big ones; agents skip approvals; what the AI learned is lost or goes stale; there is no audit trail. v2 answers all five on the user's first day.

Context

Who uses this system and how, and every outside system it talks to. The team lead is the person. Everything else is software on the same machine, except the model provider behind the AI tool and the team's own build pipeline.

Actor / external systemRelationship
Team leadRuns one install command, answers six setup questions, reads the web page, approves plans and sensitive changes. The only one who can approve; the approval records his name and the time.
Lead agentThe AI session the team lead talks to, for example Claude Code. Learns the codebase, asks the questions the code cannot answer, turns requests into work items, plans them, starts task agents, reports back. It does not write code.
Task agentA short-lived AI session the lead agent starts for one piece of work. Receives a brief with only what that task needs, writes code and tests, runs them, reports back with the result and the cost.
AI reviewerA task agent in the reviewer role. Reads the change against the rules and the plan, records findings, approves or sends it back. Never the same session that wrote the code.
AI toolClaude Code, Cursor or Codex. Hosts every agent session and reads Codeloop through its tools (MCP) and the files Codeloop adds to the repository.
Model providerThe service the AI tool calls for its model. Prompts and code the agents read go there under the AI tool's own terms. Codeloop itself sends nothing anywhere.
Git repositoryHolds the code and Codeloop's own files: the knowledge base, decisions, rules and the board. Commits carry the work item they belong to.
Build pipelineThe team's existing automated checks. "Done" means these pass; Codeloop reads the result and does not replace them.
Test suiteThe team's existing tests. Codeloop runs them during learning to find the commands that work, and task agents run them as proof.

The three parts and the loop

Codeloop has three parts, all running on the user's own machine.

PartWhat it does
Codeloop serverHolds the board (every work item and where it stands), the knowledge base (what it has learned about the system), the team's decisions and rules, and the record of every action. Shows them on a web page and serves them to agents.
Lead agentThe AI session the user talks to. It turns requests into work items, plans them, starts other agents, and reports back. It does not write code itself.
Task agentsShort-lived AI sessions the lead agent starts, one per piece of work: one writes code, another reviews it. Each gets a brief with only what that task needs.

Every piece of work follows the same loop.

request --> work item --> for each step the team chose:
                           1. Codeloop gives the agent the context for this step
                              (the plan, past decisions, rules, relevant knowledge)
                           2. the agent does the step and reports back with proof
                           3. Codeloop checks the proof and records the result
                           4. if the step needs approval, it waits for a named person
                        --> done --> lessons go back into the knowledge base
PropertyWhat it means
ControlledAgents cannot approve their own work. Codeloop enforces the approvals, so the control does not depend on the agent's good behaviour.
TraceableEvery action records who did it, in what role, why, and what it cost.
CurrentA work item's status comes from the real code changes and test results. Knowledge pages are flagged when the code they describe changes.
PortableEverything is plain files in the repository plus a local server. It works with Claude Code, Cursor and Codex, and nothing goes to a Codeloop cloud.
Any languageCodeloop uses the build and test commands it finds in the repository. Stack packs add conventions and checks per stack: Java, Python, TypeScript, Go and .NET first.

Data stores

What Codeloop keeps, all as files in the repository. A work item's stage is computed from its documents, the approvals on them, its hand-backs and its commits, by one function that the board, the command line and the warnings all use.

DataWhat it holds
BoardEvery work item: its kind (feature, task or bug), size, plan, questions and answers, approvals, hand-backs, commits, cost, and the stage computed from all of these.
Knowledge baseWhat Codeloop learned about the system: each module and the data it owns, the build and test commands that really work and how long they take, where change is risky, the conventions in use. Each page carries the commit it was checked against and is flagged when the code it describes changes.
DecisionsEvery answer the team lead gave, with the question, the source, the date and the scope. Searched before any agent asks him again. A newer decision replaces an older one; none is deleted.
RulesWhat must never happen, and the conventions kept as rules the AI must follow. Each rule carries a date and the reason.
RecordEvery action: who did it, in what role, why, and the cost. Approvals name the person and the time.

The screens

Each step of the first day has a screen in the Codeloop web page. They are built as real pages in Codeloop's own app, from its existing components, with real data. The existing Home, Inbox, Wiki, Settings and Setup pages are extended; none is replaced.

StepScreenWhat the user sees and does
1 to 3Getting startedWhat Codeloop found (languages, tools, modules), the learning progress, then the ten-line summary
4Setup questionsSix questions with recommended answers, "accept all", and the preset with each step switchable
5KnowledgeThe learned pages marked draft or confirmed, the decisions, the rules, and corrections in place
5Work processHis steps and approval points laid out; switch a step on or off, change who approves
6Work itemThe plan, the questions asked and answered, the approval button, the agents' reports with proof and cost, the review findings
6AgentsThe lead agent and task agents: which are working, on what, and since when; the agent roles and what each may do
8HomeWhat waits for him, worked versus waiting, cost, and the warnings

What Codeloop decides for you, and what you can change

Defaults, so a team starts without designing a process: three presets for how much process a change gets (Light, Standard, Controlled); one lead agent per repository; task agents split by area so two never edit the same files; a separate reviewer; "done" means the existing automated checks pass; learning the system comes before the first work item.

Everything can be changed: steps, approval points, agent roles, rules, checks, and add-on packs that bundle them. The setup questions and the web page change the same settings, so there is one source of truth.

PresetSteps
LightBuild, review, done.
Standard, recommendedClarifying questions and a written plan for medium or larger work, then build, review, done. Screen designs only when a change has a screen.
ControlledAdds research, recorded test evidence and an approval before release to production.

Delivery

Before any code, this plan is published inside Codeloop as the system design and the first-day workflow, and the owner reviews it there. The existing open fixes finish first, in about a week. The current version is then frozen for our own production project so it is never disrupted, and v2 is built beside it, with at most two AI builders at a time.

Proof: the eight first-day steps run on two real services in different languages, for example Netflix Dispatch (Python) and a large open-source Spring Boot service (Java), recording setup time, questions accepted as recommended, time to first approval, time to done, how often a person stepped in, and AI cost; then the owner runs it himself. A head-to-head builds the same feature on three copies of one service with Spec Kit, BMAD and Codeloop. After every v2 install, our production project is checked to be untouched.

Risks

  • "Nothing is sent to a vendor's cloud" holds for Codeloop, and the AI tool still sends prompts and the code it reads to its model provider under its own terms. The public page says this plainly; it is confirmed before the page ships.
  • Learning a very large repository takes longer than ten minutes, or a build command hangs. Mitigation: each command runs with a time limit, the summary says which commands were skipped, and the user can confirm the commands by hand.
  • The recommended answers to the six questions are wrong for a team. Mitigation: every answer is editable on the Setup questions and Work process screens, and each change is a recorded decision.
  • AI cost is high or unpredictable, as users report of other tools. Mitigation: a cap on how many agents run, a budget per item, and cost shown on every item and on Home.
  • Building v2 disrupts our own production project. Mitigation: the current version is frozen for that project first (phase 0), and every v2 install is checked against it.
  • Stack detection misses a language or build tool in the trial repository. Mitigation: the five stacks named first are the ones the trial services use; an undetected stack falls back to the generic path and says so on Getting started.
  • A screen is built that cannot be assembled from the app's existing components. Mitigation: screens are built in the app from the approved three-parts frames, and each is checked at 1280 px and 400 px beside its frame.
  • The head-to-head needs more AI calls than the usual limit of ten per experiment. Mitigation: the owner approves the budget before it runs.

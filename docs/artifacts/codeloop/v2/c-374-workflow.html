Codeloop v2: the user's first day

c-374 · codeloop · v2 · workflow

A team lead installs Codeloop on an existing service, Codeloop learns the system and asks six questions, and the first feature and the first bug go from request to done through the lead agent, a task agent and a reviewer, with every approval recorded against a named person.

User Lead agent Codeloop server Task agent Reviewer

Status: proposal, 20 October 2026, written from the approved v2 plan for the owner's review. The user is a team lead with an existing service his team has run for years: a large codebase in any language, a database, a test suite and a build pipeline. He uses Claude Code in this example. From day one Codeloop is where new work is tracked; the old tracker stays as it is.

Install and learn (steps 1 to 3)

Trigger: one command in the repository. Outcome: a drafted knowledge base, a ten-line summary, and an AI tool that already knows it is the lead agent. Screen: Getting started.

  Server->>Server: detect languages, frameworks, build and test tools, database, pipeline, main modules

  User->>Lead: opens the AI tool
  Lead->>Server: read role and brief for this repository
  Server-->>Lead: role is lead agent, first job is learn, then ask
  Lead-->>User: I am the lead agent for this repository, learning the codebase now
  Lead->>Server: start learning
  Server->>Server: run each build and test command, record result and time

  Server-->>Lead: draft knowledge pages, marked draft

Task agent builds (step 6, part 5)

Trigger: the plan is approved. Outcome: code and tests written and run, a hand-back with the result and the cost, commits linked to the work item. Screens: Agents, Work item.

Entity state

The work item. Its stage is computed from its documents, the approvals on them, its hand-backs and its commits; nobody types it. A bug enters at Building directly.

stateDiagram-v2
  [*] --> Requested
  Requested --> Planned: lead agent writes the plan
  Requested --> Building: bug, short route
  Planned --> Requested: rejected with a note
  Planned --> Approved: a named person approves
  Approved --> Building: task agent briefed
  Building --> Review: hand-back with proof accepted
  Building --> Building: hand-back with failing proof
  Review --> Building: findings sent back
  Review --> Checking: reviewer approves
  Checking --> Building: pipeline fails
  Checking --> Done: pipeline passes
  Done --> [*]

Actors and entities

ActorRole in this workflow
UserThe team lead. Installs, answers six questions, corrects one detail, approves plans and sensitive changes, reads Home. The only one who can approve.
Lead agentThe AI session he talks to. Learns, asks, sizes requests, searches decisions before asking, plans, starts task agents and the reviewer, reports in one paragraph. Writes no code.
Codeloop serverHolds the board, the knowledge base, the decisions, the rules and the record. Serves briefs, checks proof, enforces who may approve, computes stage and warnings.
Task agentA short-lived session per piece of work. Writes code and tests, runs them, hands back with commit range, proof and cost.
ReviewerA separate session that reads the change against the plan and the rules and records findings and a verdict. Never the session that wrote the code.
EntityLifecycle owner
Work itemCodeloop server; stage computed from its documents, approvals, hand-backs and commits.
DecisionCodeloop server; created on every answer and approval by a person, replaced by a newer decision, never deleted.
Knowledge pageCodeloop server; drafted by learning, confirmed or corrected by the user, flagged when the code it describes changes.
Hand-backTask agent writes it; Codeloop server checks it and moves the item.

Codeloop v2 implementation plan

c-321 · codeloop · v2 · implementation plan

How v2.0 is built, tested, moved onto real boards and switched on, story by story, without touching what the production project runs until v2 has proven itself.

Status: plan for the owner's review, written 17 October 2026. Planning only: no code is written until the owner approves the stories. Built from the Codeloop Cloud architecture v2 page (c-321-system-design.html, beside this page), the day-one release agreed by the production project's orchestrator and the owner, and cards c-321, c-322, c-324, c-325, c-326, c-327 and c-328.

Goal

Codeloop v2.0 moves the board out of the shared cards.json file into a store that only the local hub writes, makes the command line, the hooks and the agents clients of that hub, gives agents an MCP link over HTTP for stories and search, and adds review findings on the story, approve with conditions, priority that can pause work, an agent named for each lane stage, and live presence of agent sessions. An agent is a definition (a persona, the skills it may run, its tools and MCP access, a preferred model or host); an agent session is a running instance of one. That is steps 1 to 3 of the architecture page, the day-one release, plus step 4, story documents in the store, with nothing hosted. It ships in four phases: freeze v1 as a packed release, build v2 beside it under its own command name and home, run codeloop's own board on it, then switch the production project with a rehearsed rollback. The production project keeps running the exact v1 it runs today until codeloop itself runs well on v2 with a successful migration and a dry run of the production project's migration passes. The production project then moves in one switch: board, wiki and story documents together.

Out of scope for v2.0

  • Codeloop Cloud as the record and one identity with the Connect page (steps 5 and 6, card c-322).
  • The constitution, a cast shared across a Cloud workspace, and delegated approvals by a named orchestrator (step 7, the second half of c-327). Agent definitions per stage are in v2.0 (c-326). The event field for "on behalf of" exists from S1.6, so delegation needs no migration later.
  • Public publishing (step 8, card c-323).
  • Soft locks on files, provisional writes while the server is down, the web board's visual redesign, a hook file for Codex, links between projects.
  • Importing review files kept in other repositories. Findings start fresh in v2.

Epics and stories

Six epics, 35 stories: 32 new cards proposed and waiting for the owner, c-329 to c-360 (one parent card for the isolation and cutover epics, 31 stories), and four cards already on the board placed as stories (c-324, c-326, c-327, c-328). c-321 is the parent of steps 1 and 4, c-325 of step 2. Epics are listed in the order they ship: E5, story documents, comes before E4's last story, the switch. c-321's current title and research describe per-story folders in git, which the architecture's version 2 dropped, so the owner should retitle it "The hub owns the board's record, imported from today's board" or close it once its children are approved. Every story is S or M by the story standard, has at most eight tasks in codeloop's task format, one to five acceptance lines, and its failure modes with one test each.

A board moved to v2 refuses writes from v1

S0.1 · card c-330 · parent c-329 · feature install-and-import · persona founder · size S, 0.5 days · needs nothing; lands on main before the freeze so it is inside the frozen build

Isolation and cutover

What is shared today. The global codeloop is an npm link to the codeloop checkout/dist, so every build in the checkout changes what the production project runs at once. One v1 home, ~/.codeloop, holds the hub registry with both projects, one hub.json (port 4050, token, pid), one hook socket, and the production project's board itself, because the production project's cards.json is a link into the v1 home. Workers in the checkout run board commands as node dist/index.js, which is v1 today and becomes v2 the day v2 work starts. Each of these is handled below.

Phase A, freeze v1 (S0.1, S0.2)

  1. S0.1, the moved-board refusal, lands on main first, so the frozen build already knows how to step aside.
  2. The in-flight branch merges to main. main gets version 1.0.0 and the tag v1.0.0 at a named sha; that sha is the freeze.
  3. release-pack.sh exports the tag with git archive into a scratch folder, runs npm ci and npm run build:all there, and packs into ~/.codeloop/releases with a sha256 beside it. The working tree is never packed. The stray tarball in the repository root is not used.

  5. check-frozen.sh proves it: readlink on the global codeloop resolves inside the global node_modules, the package folder is a real directory, codeloop --version prints 1.0.0, no codeloop process runs a script from the checkout, and in the production project guard session exits 0 and the card count is unchanged.

Phase C, codeloop's own board on v2 (S4.1, S4.2, S4.3)

Entry: step 1 done, parity green on a copy of codeloop's board, rollback rehearsed on a copy. Then, in one coordinated step announced by the codeloop orchestrator: every worker parks (codeloop ps shows no agent), codeloop off, switch-to-v2.sh imports the board with the report passing, commits project.json and moved.json, adds codeloop-next's hooks and MCP to the untracked .claude/settings.local.json (the repository has no codeloop hooks or MCP config today, so nothing tracked changes and no token is committed), removes the project from the v1 hub registry so the v1 board is not shown stale, then codeloop-next on. Phase D, the production project switches (S4.4)

Entry checklist, all required, checked by the switch script: codeloop runs well on v2 with its board and documents migration reports passed, in the owner's judgement; a dry run of the production project's migration passes, run with switch-to-v2.sh --dry-run on a copy of the project and of the v1 home, moving board, wiki and documents and changing nothing real; every v2.0 story shipped, step 4 included; two rollback rehearsals on copies, each under ten minutes; the owner approves the gate on S4.4. The switch runs at a quiet time, outside the hourly scheduled run:

  1. Park the production project's orchestrator and its agents; wait for the run lock; codeloop off.
  2. Snapshot the production project's .codeloop and the v1 home into ~/.codeloop/releases with a sha256.
  3. Remove the v1 schedule line with codeloop schedule remove, never by editing crontab.
  4. Install the v2.0.0 tarball globally, packed by the same release script with the stable channel.
  5. codeloop import in the production project, board, wiki and documents in one run: every report passes, or the script stops and runs the rollback.
  6. Restore settings: the hook commands keep their v1 shapes and need no change; .mcp.json keeps working through the stdio bridge. codeloop schedule install writes v2's line.
  7. Smoke: the production project's orchestrator's daily commands, guard session, a card count equal to the report. codeloop on.

The watch lasts five working days, with a v1-format export written after each change (30-second debounce) so a rollback loses at most that much. Triggers for rollback: any lost or changed record in the nightly round trip; hooks refusing edits v1 would allow for 15 minutes; the production project's orchestrator blocked by codeloop for 30 minutes; the owner says so.

Rollback (S4.2), data first, then the binary

  1. Park and codeloop off, so nothing writes during the rollback.
  2. Export the v2 record with export --format v1: from the hub, from the store file read-only when the hub is down, or from the continuous export when the file cannot be read. The script says which.
  3. Verify the export against the store with the migration report. The script stops here on any difference.
  4. Restore into the project: cards.json through its link, wiki pages, interview files, and every story document back to its spec folder; remove moved.json and project.json; commit the restored files by path.
  5. Stop the v2 hub; reinstall the frozen 1.0.0 tarball after checking its sha256.
  6. Restore the hook and MCP settings saved at the switch; codeloop schedule install writes v1's line; re-register the project with the v1 hub.
  7. Smoke: v1's card count equals the export's; guard session exits 0; codeloop on.

Target: under ten minutes, rehearsed twice on a copy of the production project with a copied home before the switch. The same script with --channel next rolls codeloop's own board back to v1 if the dogfood fails.

Risks

  • Step 1 is larger than the architecture page says. 214 direct readCards and writeCards calls in 47 files, the work of dropped card c-320, come back as S1.1 to S1.5. Step 1 is sized at 24 days here, against three to four weeks on the architecture page. Bounded by cutting it along the store README's order so each story lands and passes alone.
  • v2 work touches v1's home or the production project's board by mistake. The channel comes from the build, the next channel has its own home and port, v2 refuses v1 boards and v1 hub records, and v1-untouched.sh runs around every session.
  • A worker runs node dist/index.js on codeloop's board after the freeze. That is v2, and it refuses a v1 board with a sentence naming codeloop. Instructions change on freeze day.
  • A long-lived v1 process keeps running code from the checkout. The freeze stops the hub and hook helper and check-frozen.sh fails while any codeloop process runs a script from the checkout.
  • Import loses part of a board without anyone noticing. The report compares keys, hashes and events and fails on any difference; the round trip and parity run nightly on shadow copies of both boards for weeks before the production project moves.
  • The hub becomes a single point of failure for every command and hook. Start on demand, takeover of a stale pid, the log tail on a crash, and read-only export and doctor with the hub down. The dogfood soak counts hub restarts and hook refusals.
  • MCP callers act as members in v2.0, so an orchestrator cannot approve over MCP. The production project's orchestrator keeps approving through the command line, as in v1, until delegation arrives in step 7. This is the one open question left.
  • A v1 bug found while v2 is built. v1 is frozen as it is and gets no fixes, by the owner's decision. A v1 bug is worked around until the switch and fixed in v2.
  • Two hubs after the switch. The production project on the stable hub, codeloop's own board on the next hub. Each hub page shows its channel and links the other.
  • Documents add a second migration. Codeloop's board moves its documents on a running v2 board; the production project's moves everything at once. Both use the same import and report, and the production project's is dry-run on a copy first.
  • The calendar. The time codeloop spends on v2 is set by the owner's judgement, not a date, and the watch adds a week after the switch.

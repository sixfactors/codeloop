Codeloop Cloud architecture

c-321 · codeloop · cloud · system design · version 2

Codeloop from one laptop to a team on Codeloop Cloud, the shared context and coordination point for agents that run on your own machines: one server holds the record, locally or hosted; MCP, API, web board and command line are its clients; git is an optional export.

Status: proposal, version 2, 17 October 2026. Revised after the owner's decisions on the record, the client model, story ids, identity and publishing. Decision pending on the five open questions at the end.

Version 2, what changed since version 1

  • A server holds the record in every version. Git is an optional export and import, not a store. The per-story git folders of version 1 are dropped.
  • The command line becomes a client of the server's HTTP API. Nothing but the server writes the store.
  • Each story has a random internal id and a short readable key. Keys are assigned by the server, so two machines cannot clash.
  • The MCP carries most of codeloop's data operations, not a dozen workflow verbs: eight resource tools, each with an action argument and a role per action. The command line and the web board call the same API.
  • One identity: a codeloop account is a Protobox account. Roles come from the Protobox workspace, agents get keys from a "Connect your agents" page.
  • Public publishing is a per-project switch, later. "Which copy is the record" and "story number clashes" are closed and gone from the open questions.

The problem

Today every story on a codeloop board lives in one shared file in the repository. Every command, hook and agent rewrites that file, so a commit that stages it carries everyone else's changes, a second machine means syncing one large file both ways, and moving the file out of the repository takes the board's history out of git. Agents reach the board by launching the command line and reading its text.

Codeloop's job is visibility and context for agents across a team coding with AI: who is working on what, on which machine and branch, what was decided, and what each agent needs to know before it starts. It works with any way of structuring the work, BMAD, Spec Kit, a custom pipeline or none; its own lanes and gates are optional and configurable, one structure among several a project can run.

This design puts one server in charge of the record. Downloaded, it runs on your machine as the hub with its own store. Hosted, the same server is Codeloop Cloud: the shared context and coordination point for a team whose agents run on their own machines. Agents, the web board and the command line are all its clients. MCP (Model Context Protocol) is the standard that lets an agent in Claude Code, Cursor or Codex call tools behind one URL; the server speaks it, and plain HTTP for everything else. Codeloop Cloud never runs an agent, never merges and never touches code. Git keeps the code, and an export of the board if you want one.

Software layers

One server core, four kinds of client, two places to run it. The core holds the engine, the lanes, the checks, the role rules and the store. The HTTP API and the MCP link are its only doors. The web board and the command line are thin clients of the API; the command line adds nothing the API lacks, it only makes the API easy to call from a shell. Local and cloud run the same server with a different store behind it.

local serverCodeloop Cloudclient, no data of its own

Text version: clients (command line, web board, MCP agents, hooks) call the HTTP API or MCP; the server core decides and writes the store; locally the store is SQLite, in the cloud MongoDB; execution commands exist only locally and call the local API.

Where the local store lives

The hub keeps each project's record in one SQLite file in the codeloop home, the per-user folder ~/.codeloop that already holds the hub registry: ~/.codeloop/projects/<project id>/codeloop.db. Not inside the repository, for three reasons. Several checkouts and worktrees of one repository must see one board; a file in the repository would give each its own. A database beside tracked files is one git clean away from damage, and folder-sync tools corrupt a live database. And one folder for every project is one place to back up.

A repository finds its store through a random project id in the tracked .codeloop/project.json, written by codeloop init. The id is not a location setting: codeloop alone decides the path, and the per-project store.home, store.layout and store.move settings go away. A fresh clone has no board until codeloop import reads an export from git or the project is linked to Codeloop Cloud.

Story documents live in the store too. Research, spec, plan, tasks and evidence are documents on the story, written by agents through the documents tool or the API and read back through the same tool and the story brief. That is what "git is not the record" means in practice. The plan's file list, the lease the edit hook enforces, is read from the stored plan. codeloop export writes every story as a folder of markdown under .codeloop/export/ for an editor or a commit; whether agents may also write through a mirrored folder is question 1.

One writer: the command line as a client

Only the server process writes the store. The command line never opens the database for writing; it calls the local API, as the web board already does. Four consequences.

  • Start on demand. The first command that finds no running hub starts one in the background, as codeloop open does today: it records pid, port and token in the codeloop home, waits for the health route, then sends its request. The hub stops itself after a long idle period.
  • When it cannot start. A stale pid is taken over and a taken port replaced by the next free one. A broken build or a crash on boot is reported: the command prints the last lines of the hub log and exits non-zero. It never writes the store itself, because a second writer is the problem this design removes.
  • Hooks are clients. The guard hooks call the local API; the separate hook helper process folds into the hub. If the hub is down the hook starts it and waits a few seconds; if it still cannot answer, the edit or shell command is refused, the fail-closed behaviour hooks have today. No hook ever waits on the network.
  • Recovery is read-only. codeloop export, codeloop doctor and a plain sqlite3 read the file with the hub down, because readers do not make a second writer. A damaged store is rebuilt by the hub from the last export in git or from Codeloop Cloud.

Offline on a linked project. The hub holds a full copy and answers reads from it. A write lands in the copy as a provisional event, visible on the board, and is pushed when the cloud is reachable. The cloud orders events by fixed rules: an owner decision beats an agent one, a later owner decision beats an earlier one, and an approval whose fingerprint no longer matches the handed-back work is set aside so the gate asks again. Two contradicting owner decisions at one gate park the story for a person. One local writer, one cloud writer, a queue between them.

The MCP tool surface

The MCP is the main interface, so it carries most of what the record can do: read, create, update and delete stories, documents, wiki pages, skills, questions and summaries, as well as the workflow verbs. Sixty separate tools would fill an agent's context before it started. Instead, as Protobox's own MCP does with its knowledge and apps tools, there is one tool per resource with an action argument, an id, a data object for writes and filters for lists. Called with no action, a tool returns a menu of the actions the caller's role allows. A destructive action previews first and runs when called again with confirm. Every action is one API route, and the command line and the web board call those same routes.

Structure-specific actions (advance, check, promote) exist only when the project runs lanes; a project using its own pipeline still has every read and write.

Story keys. A key is <prefix>-<number>: one to five letters, a hyphen, one to six digits, so three to twelve characters, unique within a project. The server that holds the record assigns the number, so two machines cannot hand out the same key: the hub for a local project, Codeloop Cloud for a linked one. A story proposed offline on a linked project has an internal id at once and shows a pending key until the cloud assigns one; agents and the sync protocol never needed the key, and a commit trailer may name the internal id instead.

Migration of old ids. Today's ids already have this shape, so c-321 becomes the key c-321 of a story with a new internal id. Import sets the project prefix to c and the counter past the highest number. Commit trailers, notes and wiki links keep working unchanged.

Agents. The agent entity keeps its version 1 shape. The session file becomes an agent in state working, the lease its files-held list, the computed holder the story's current agent; the stall check sets the state when last activity passes the limit. A person working by hand is an agent of kind person. Agent records sync on every change, so a team sees every machine's agents on one board, and the cloud marks an agent stalled when its machine stops reporting.

Sync. Story events, documents (by content hash), wiki pages, skills, lanes, config and agent records flow between a hub and the cloud per item: pushed after each local write, pulled from the cloud's event stream. Lanes and config move only from an owner. Activity streams, the record of which files and commands a coding session touched, stay on the machine. Code never moves.

Migrating an existing board. codeloop import reads today's shared board file and any export folder, creates the stories with new internal ids and their old keys, and says so. From then on the file is unused; the owner may delete it from git. Export is the reverse and complete: codeloop cloud disconnect followed by an export leaves a project that can be imported anywhere, and the cloud copy can be rebuilt from any hub that holds the project.

Identity, roles and credentials

Nobody signs up twice. A codeloop sign-up creates a Protobox account and a workspace behind it, and an existing Protobox user signs in with that account. Protobox already provides accounts with verified email, workspaces with members and invitations, roles, and API keys with a kind and a workspace or project scope. What it lacks is a way for a command line to sign in without a password prompt; that is the device flow below, new work on Protobox.

Four Protobox roles map onto three codeloop roles for people; owner and admin both decide, because splitting them has no use on a board. The builder role is never a person's: it comes from an agent key, minted on the Connect page, named for the agent and machine, attributed to the person who minted it. The personal token from codeloop login carries the person's own role and is what the command line uses. MCP clients can send only a bearer header, so the key is the whole identity: its kind decides the role, no tool argument can raise it, and the server checks the role on every call. A refusal names the role that could have done it.

Public publishing, later

An owner chooses per project to publish the board and wiki at a public URL, read-only, through a privacy filter: deny by default, nothing marked private, no agent records, no specs before their gate, no evidence files, no keys or members, and every served text passes a machine-path scan that withholds a matching line with a marker. Activity streams are never in the cloud at all.

Docs platforms such as Mintlify already run this shape. Worth borrowing: a per-page public flag that can also be set for a whole group, so publishing is explicit and inspectable; "hidden" kept separate from "private", because a hidden page is still reachable by URL, so concealment is never used as access control; a noindex marker on pages reachable but not meant to be found; a stable public URL per project, custom domain later. Where codeloop differs: Mintlify's pages are public unless protected, codeloop's are private unless an owner publishes, because a board carries unfinished work.

Steps

Six steps, each usable on its own. Sizes use the board's scale (S, M, L) with a rough calendar reading. The order follows dependencies: everything after step 1 needs one writer and a stable story id, so the store moves first; roles and keys need the server to be the only door, so hooks and MCP move next; the cloud is the same server with a second store, so it comes once the server is whole; identity and the Connect page need the cloud to exist; publishing is last because it is read-only on top of all of it.

Risks and what stays out of scope

  • The hub will not start on some machine. The command shows the log and exits; doctor and export still read the store. Nothing writes around the server.
  • Protobox is down. A linked project keeps working from the hub's copy with provisional writes; the shared board is stale until it returns.
  • A merge-rule bug misplaces a story. History is add-only and replay deterministic, so any story can be replayed and the difference shown.
  • Private text reaches the public view. Deny by default, activity never leaves the machine, the path scan withholds matches, and one test feeds the view a story built to leak.
  • codeloop releases become tied to Protobox deploys. The API and sync protocol are versioned; the command line refuses a server it does not understand.
  • Pressure to make the cloud do the work. The hosted API has no verb for merge, gate run, orchestrated run or builder start, so the line holds by construction.

Out of scope here: Protobox internals beyond identity; the web board's visual redesign; running agents in the cloud, by design; a hook file for Codex; links between projects; live shared editing of a document.

Open questions

1. How do agents write a story's documents: research, spec, plan, evidence?

Options: (a) only through the documents tool and the API, with codeloop export for reading in an editor; (b) through a folder the hub mirrors and watches, so an agent can edit markdown as today. Recommendation: (a). A watched folder is a second writer by another name, and stage agents already receive and return text through the brief.

2. Should an agent use a key of its own, or its person's token?

Options: (a) one agent key per agent host per machine, minted on Connect your agents and attributed to the person; (b) each person's login token, reused by every agent they run. Recommendation: (a). A leaked key is revoked alone, presence shows which agent, and a person's token can never be made to approve by an agent.

3. On a linked project with no network, may the hub accept writes?

Options: (a) yes, as provisional events the cloud orders and resolves by the fixed rules when they arrive; (b) read-only until the cloud is back. Recommendation: (a). A solo founder on a train keeps working; the provisional mark and the owner-wins rules keep the record honest.

4. When a P1 arrives, what happens to a P2 a builder is working on?

Options: (a) park it automatically with a note after the builder's uncommitted work is handed back; (b) ask the owner first; (c) no pause, the P1 waits for a free slot. Recommendation: (b) now, moving to (a) once hand-back on pause exists.

5. Where should checks such as size budget and health measure by default?

Options: (a) the story's branch against main; (b) main itself; (c) the branch the agent is on. Recommendation: (c), right for a founder running several agents on one branch and for a team on one worktree per story; a project can set (a) or (b).

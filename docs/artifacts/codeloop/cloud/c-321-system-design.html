Codeloop Cloud architecture

c-321 · codeloop · cloud · system design

Codeloop from one laptop to a team on Codeloop Cloud, the shared context and coordination point for agents that run on your own machines: what runs where, which copy is the record, and the steps to get there.

Status: proposal, 17 October 2026. Decision pending on the open questions at the end.

The problem

Every story on a codeloop board lives in one shared file. Every agent and person writes to it, so a commit that stages it carries everyone else's unsaved changes, and moving the file out of the repository takes the board's history out of git. Sharing with a second machine means syncing one large file both ways. Agents reach the board by launching the command line and reading its text.

This design gives each story its own folder in git, holding its state and an add-only history beside its plan and evidence. One local process, the hub, serves the web board and an MCP link from the same core library the command line uses. MCP (Model Context Protocol) is the standard that lets an agent in Claude Code, Cursor or Codex call tools behind one URL. Codeloop Cloud, on Protobox, is the central context and coordination point for a team's own agents: the board, the wiki and knowledge base, skills, and agent presence, served over a hosted board and one MCP link, with a filtered public view. It never runs an agent, never merges, and never touches anyone's code or git. Agents run on members' machines in Claude Code, Cursor or Codex and report in. Each step below works on its own.

Software layers

Five layers, the same on your machine and in the cloud. The command line and the web board are thin peers: both call the core library, which holds the engine, the lanes, the checks and the role rules. Every decision about a story is made there.

in gitCodeloop Cloudprocess, no data of its own

Which process owns writes. On your machine there is no single writer. The command line, the hook helper (a resident process answering the hooks over a local socket) and the hub each load the core library and write a story's files directly, under a lock on that story's folder, so no command waits for the hub and no hook waits for anything but the disk. In the cloud the hosted service is the only writer to the database and checks the caller's role on every call. It runs the coordination part of the core library only: board, wiki, skills, presence. Everything that executes, the orchestrated turn, worktrees, merge, gate runs, scheduled agent runs, exists only in the downloadable version on a machine with the code.

Local only, open source

Open source is Codeloop Cloud run on your own machine: the same product, the same commands and board, with the features that need a server left out. You install one package and run codeloop init in a project. From then on every command writes files under .codeloop. No server, no account, no network. Linking adds sharing and takes nothing away.

One layout for every project. codeloop decides the folder names, a project on the older layout is moved on its first command, and the settings that let a project pick where its files go are removed. A story's folder holds everything about it:

.codeloop/
  stories/321/
    state.json       stage, gate, priority, size, feature, awaiting   (replayed from history)
    history.jsonl    one line per event, add-only: propose, promote, approve, answer, park …
    research.md  spec.md  plan.md  tasks.md
    evidence/        verify.md, use-case results
    mock.html
  wiki/  lanes/  config.yaml                       shared, in git
  state/agents/<id>.json                           who is working what, where; not in git
  state/activity/321.jsonl                        every edit, command and prompt; not in git

Two per-story files, on purpose. The history is the board's record: decisions, stage moves, notes, who made each. The activity stream is what a coding session did: file paths, shell commands, prompt text. It stays on the machine, outside git, because it holds exactly what the public view must never carry.

When the hub is down. The hub serves the web board and the MCP link, nothing else. Every command and hook still works, because they open the story files themselves. An agent on the MCP link falls back to the command line, which its skill already knows. codeloop open starts the hub again. Hooks never call the hub or the network.

Cloud connected, team

Which copy is the record

Option 1: git files stay the record, the cloud is a synced mirror. Linking changes nothing. But two machines hold two records, the mirror has to merge them to show one board, and roles are enforced only inside each machine's process, so nothing stops an altered client from writing an approval.

Option 2: for a linked project the cloud is the record; the git files are a complete export codeloop keeps current on every machine. One place hands out story numbers, orders events, enforces roles and serves the public view. Offline writes are provisional until they arrive, and shared work depends on Protobox being up.

Recommended: option 2, with one rule: the export is complete. codeloop cloud disconnect leaves a project identical to one never linked, and the cloud copy can be rebuilt from any up-to-date checkout.

Two machines or two people on one story

Every history event carries the story id, a time, who made it and a random event id; nothing is edited or removed. Merging two copies of a story is the union of their events, sorted by time then event id, and the state file is replayed from the result, so state is never merged by hand.

Most pairs of events do not touch: a note and a task tick both stay. Where two decide the same thing, the rules are fixed: an owner decision beats an agent one; a later owner decision beats an earlier one; an approval whose fingerprint no longer matches the handed-back work is set aside and the gate asks again, as the engine already does. Only two owner decisions that contradict each other at the same gate park the story, with both notes, for a person.

Two machines can also propose at the same moment and pick the same number. The cloud hands each linked machine a block of numbers at link time, so numbers never collide and never change (question 2).

Offline

Everything local works offline. A write lands in the story files first and is marked pending; the next command, or the hub, pushes it. Today's sync writes the cloud before the local file and blocks on the network; this design reverses the order, and no hook ever waits for the network.

Agents through one URL

Protobox gives every workspace one MCP endpoint, <workspace>.protobox.app/mcp. Codeloop Cloud registers its tools there, so an agent adds one URL and one key and sees the same dozen tools the local hub serves: next up, get story, advance, task done, hand back, note, ask, propose, check, brief, and the owner-only approve and answer. MCP clients can send only an Authorization: Bearer header, so the key is the whole identity: its kind decides the caller's role, and no tool argument can raise it. On a linked project an agent may use either link; both end in the same record.

What the cloud does not expose. The hosted API and MCP have no merge, gate-run, orchestrated-run or start-builder action. Those stay commands of the downloadable version, on the machine that has the code and the agent. The cloud records what they did.

Checks run where the code is. Size budget, health and the stage checks run locally, by the command line or the hook, and their results sync as events. Where a check measures is a user preference: the story's branch, main, or the branch the agent is on, because a solo founder may run several agents on one branch while a team uses one worktree per story (question 6).

Agents and people

When several people work from their own machines, the board must answer at a glance: which agent, started by whom, on whose machine, is on which story and branch right now, and is it working, waiting or stalled. Today that answer is spread over a session file per live host session, a lease file per orchestrated turn, a holder computed from the story's events, and an idle check over the activity stream. None of it leaves the machine.

The design makes the agent a first-class item in the data model. A person is a team member with a role and the machines they sign in from. An agent belongs to a person and to one story at a time:

Agent fieldHolds
idRandom, assigned when the agent starts
kindClaude Code, Cursor, Codex, CI
personWho started it; a scheduled or CI run names the person whose key it uses
machineThe machine name it runs on
project, story, branchWhat it works on, and the git branch its commits land on
started at, last activityTimes; last activity is updated by hooks and tool calls, never by the doctor's own nudge
stateworking, waiting on owner, stalled, done
files heldThe plan's file list it holds while working, the lease

A story gains two fields: its branch, and the agents that worked it, current and past, with their person and machine. The board's row for a story reads "Claude Code, started by Ana on her laptop, on branch feat/sync, working, last seen 3 minutes ago", and the needs-you feed lists every agent in the waiting state across the team.

What it replaces. The session file becomes an agent record in state working. The lease file becomes the agent's files-held list; the edit hook refuses another agent's edit to a held file as today, reading the record instead. The computed holder becomes the story's current agent. The stall check sets state to stalled when last activity passes the limit, instead of deriving it on each read. A person working by hand is an agent of kind "person" on their own machine, so one query covers everyone.

How it syncs. An agent record is written by the local agent, through the hooks and the MCP tools, or by the command line that started it. The cloud never starts an agent; it only receives reports. Records live in .codeloop/state/agents/ outside git, because they describe a moment on a machine, not the story. On a linked project they sync on every change, so every member sees every machine's agents, and the cloud marks an agent stalled when its machine stops reporting. The story's agents list is part of its history, so it is in git and travels with the story.

Identity, roles and permissions

codeloop already knows three roles: owner, reviewer and agent. Cloud adds team member and public visitor. The founder is an owner; a project can have more than one.

How a role is enforced. Locally the role comes from the process: a person's shell is owner, a process started by codeloop run --agent is agent and cannot say otherwise. On the local hub a signed-in session is owner and the start-up token is agent. In the cloud, Protobox sign-in gives a person an identity, workspace membership gives the role, and each API key is minted for one role. The hosted service checks the role on every API and MCP call, whatever the client claimed; the local check only shapes the message. A refusal is a structured error naming the role that could do it.

What the public view filters. Deny by default: a project is public only when an owner turns it on, and a story, note or page marked private stays out. Of a public project the view serves titles, user stories, stage, gate, size, priority, feature, history events, specs and plans of stories past their spec gate, evidence summaries, and wiki pages marked public. It never serves activity streams (not in the cloud at all), agent records, specs before their gate, evidence files (a screenshot may show a machine), keys, sessions or members. Every text it serves passes a machine-path scan; a matching line is withheld with a marker, so a leak shows up in a test that feeds the view a worst-case story.

Migration path

Seven steps, each usable on its own and shipped in this order. Sizes use the board's scale (S, M, L) with a rough calendar reading.

Risks and what stays out of scope

  • A merge-rule bug misplaces a story. The history is add-only and replay is deterministic, so codeloop doctor can replay any story from git and show the difference.
  • Protobox is down. Local work continues and queues; the shared board is stale until it returns. A team that cannot wait reads the git export.
  • Private text reaches the public view. Deny by default, activity streams never leave the machine, the path scan withholds matches, and one test feeds the view a story built to leak.
  • Local and server role checks drift. The server's check is final; the local one only shapes the message.
  • codeloop releases become tied to Protobox deploys. The sync and MCP endpoints are versioned, and the command line refuses a server it does not understand with a clear message.
  • Story-number collisions on two machines until the number blocks ship with step 5.
  • Pressure to make the cloud "do the work". Every execution feature stays in the downloadable version; the cloud's API has no verb for it, so the line holds by construction.

Out of scope here: Protobox internals; the web board's visual redesign; running builder agents in the cloud, by design; a hook file for Codex; links between projects; live shared editing of a spec file, which git handles.

Open questions

1. When a project is linked to Codeloop Cloud, which copy is the record?

Options: (a) the git files stay the record and the cloud is a synced mirror; (b) the cloud is the record for linked projects and the git files are a complete export codeloop keeps current. Recommendation: (b), with disconnect guaranteed to leave the project as if never linked.

2. How do two machines avoid picking the same story number?

Options: (a) the cloud hands each linked machine a block of numbers at link time; (b) offline stories get a temporary id and are renumbered when they sync; (c) ids become random strings. Recommendation: (a); numbers never change, so commit trailers and notes stay right.

3. How do teammates sign in?

Options: (a) Protobox accounts only, roles from the workspace; (b) codeloop's own invite links and passwords. Recommendation: (a); the local hub password stays for a machine with no cloud link.

4. How does the public demo stay current?

Options: (a) live from the cloud record through the filter, with a per-project switch; (b) a snapshot an owner publishes by hand. Recommendation: (a); a snapshot adds a step that gets forgotten and shows a stale loop.

5. When a P1 arrives, what happens to a P2 a builder is working on?

Options: (a) park it automatically with a note, after the builder's uncommitted work is handed back; (b) ask the owner first; (c) no pause, the P1 waits for a free slot. Recommendation: (b) now, moving to (a) once hand-back on pause exists.

6. Where should checks such as size budget and health measure by default?

Options: (a) the story's branch against main; (b) main itself; (c) the branch the agent is on, whatever it is. Recommendation: (c) as the default, since it is right for a founder running several agents on one branch and for a team on one worktree per story; a project can set (a) or (b).

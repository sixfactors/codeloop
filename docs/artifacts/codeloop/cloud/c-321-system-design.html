Codeloop Cloud architecture

c-321 · codeloop · cloud · system design · version 2

Codeloop from one laptop to a team on Codeloop Cloud, the shared context and coordination point for agents that run on your own machines: one server holds the record, locally or hosted; MCP, API, web board and command line are its clients; git is an optional export.

Status: proposal, version 2, 17 October 2026. Revised after the owner's decisions on the record, the client model, story ids, identity and publishing. Revised again the same day with the owner's answers on story documents, agent sign-in, working without the server, steps, delegated approvals, the MCP shape, reviews and the day-one release. Decision pending on the three open questions at the end.

Version 2, what changed since version 1

  • A server holds the record in every version. Git is an optional export and import, not a store. The per-story git folders of version 1 are dropped.
  • The command line becomes a client of the server's HTTP API. Nothing but the server writes the store.
  • Each story has a random internal id and a short readable key. Keys are assigned by the server, so two machines cannot clash.
  • The MCP carries most of codeloop's data operations, not a dozen workflow verbs: eight resource tools, each with an action argument and a role per action. The command line and the web board call the same API.
  • One identity: a codeloop account is a Protobox account. Roles come from the Protobox workspace. Agents use their person's sign-in, set up from a "Connect your agents" page.
  • Public publishing is a per-project switch, later. "Which copy is the record" and "story number clashes" are closed and gone from the open questions.
  • Four more questions closed: agents write story documents only through the MCP and the API; agents use their person's sign-in, not keys of their own; when the server cannot be reached, writes are refused; steps (lanes) are set per team and, in Cloud, shared per workspace with named agents.
  • New: a review is an object on the story, with findings that route to the story's agent and close when a commit fixes them; an owner can approve with conditions in one action; an owner can delegate approvals to a named orchestrator. The steps are re-cut so a day-one release ships the server record, the stories MCP with search, reviews, priority and live presence, with nothing hosted.

The problem

Today every story on a codeloop board lives in one shared file in the repository. Every command, hook and agent rewrites that file, so a commit that stages it carries everyone else's changes, a second machine means syncing one large file both ways, and moving the file out of the repository takes the board's history out of git. Agents reach the board by launching the command line and reading its text.

Codeloop's job is visibility and context for agents across a team coding with AI: who is working on what, on which machine and branch, what was decided, and what each agent needs to know before it starts. It works with any way of structuring the work, BMAD, Spec Kit, a custom pipeline or none; its own lanes and gates are optional and configurable, one structure among several a project can run.

This design puts one server in charge of the record. Downloaded, it runs on your machine as the hub with its own store. Hosted, the same server is Codeloop Cloud: the shared context and coordination point for a team whose agents run on their own machines. Agents, the web board and the command line are all its clients. MCP (Model Context Protocol) is the standard that lets an agent in Claude Code, Cursor or Codex call tools behind one URL; the server speaks it, and plain HTTP for everything else. Codeloop Cloud never runs an agent, never merges and never touches code. Git keeps the code, and an export of the board if you want one.

Software layers

One server core, four kinds of client, two places to run it. The core holds the engine, the lanes, the checks, the role rules and the store. The HTTP API and the MCP link are its only doors. The web board and the command line are thin clients of the API; the command line adds nothing the API lacks, it only makes the API easy to call from a shell. Local and cloud run the same server with a different store behind it.

local serverCodeloop Cloudclient, no data of its own

Text version: clients (command line, web board, MCP agents, hooks) call the HTTP API or MCP; the server core decides and writes the store; locally the store is SQLite, in the cloud MongoDB; execution commands exist only locally and call the local API.

Where the local store lives

The hub keeps each project's record in one SQLite file in the codeloop home, the per-user folder ~/.codeloop that already holds the hub registry: ~/.codeloop/projects/<project id>/codeloop.db. Not inside the repository, for three reasons. Several checkouts and worktrees of one repository must see one board; a file in the repository would give each its own. A database beside tracked files is one git clean away from damage, and folder-sync tools corrupt a live database. And one folder for every project is one place to back up.

A repository finds its store through a random project id in the tracked .codeloop/project.json, written by codeloop init. The id is not a location setting: codeloop alone decides the path, and the per-project store.home, store.layout and store.move settings go away. A fresh clone has no board until codeloop import reads an export from git or the project is linked to Codeloop Cloud.

Story documents live in the store too, from step 4. Until then they stay files in the story's spec folder, as today. Research, spec, plan, tasks and evidence are documents on the story, written by agents through the documents tool or the API and read back through the same tool and the story brief. That is what "git is not the record" means in practice. The plan's file list, the lease the edit hook enforces, is read from the stored plan. codeloop export writes every story as a folder of markdown under .codeloop/export/ for an editor or a commit. Agents write documents only through the tool and the API, never through a mirrored folder, because a watched folder would be a second writer.

One writer: the command line as a client

Only the server process writes the store. The command line never opens the database for writing; it calls the local API, as the web board already does. Four consequences.

  • Start on demand. The first command that finds no running hub starts one in the background, as codeloop open does today: it records pid, port and token in the codeloop home, waits for the health route, then sends its request. The hub stops itself after a long idle period.
  • When it cannot start. A stale pid is taken over and a taken port replaced by the next free one. A broken build or a crash on boot is reported: the command prints the last lines of the hub log and exits non-zero. It never writes the store itself, because a second writer is the problem this design removes.
  • Hooks are clients. The guard hooks call the local API; the separate hook helper process folds into the hub. If the hub is down the hook starts it and waits a few seconds; if it still cannot answer, the edit or shell command is refused, the fail-closed behaviour hooks have today. No hook ever waits on the network.
  • Recovery is read-only. codeloop export, codeloop doctor and a plain sqlite3 read the file with the hub down, because readers do not make a second writer. A damaged store is rebuilt by the hub from the last export in git or from Codeloop Cloud.

When the server cannot be reached. Every client talks to one server: the hub for a local project, the remote server for a linked one. In version 1, when that server does not answer, codeloop says "server not available" and refuses the write. Nothing is queued or written around it. Provisional writes made offline and merged later are an option for a later version.

The MCP tool surface

The MCP is the main interface, so it carries most of what the record can do: read, create, update and delete stories, reviews, documents, wiki pages, skills and questions, as well as the workflow verbs. Sixty separate tools would fill an agent's context before it started. Instead, as Protobox's own MCP does with its knowledge and apps tools, there are eight grouped tools, one per resource, each with an action argument, plus one search tool across the record. Every action is one API route, and the command line and the web board call those same routes. The design follows MCP specification version 2026-07-28.

The day-one release ships stories (get, task_done, handback, note), reviews, search and approve_with_conditions; the rest follow with the steps that need them.

Typed inputs per action. Each tool's inputSchema is a JSON Schema 2020-12 oneOf with one branch per action, keyed on action, so an agent sees exactly which fields each action takes and the client can validate before it calls. Each tool has an outputSchema; results carry structuredContent and, as the specification asks for compatibility, the same JSON as text. Called with no action, a tool returns the actions the caller's role allows. A destructive action previews first and runs when called again with confirm. List actions page with the specification's opaque cursor.

Clear errors. The specification separates two kinds. A malformed request or an unknown tool is a JSON-RPC protocol error. Everything an agent can correct, a missing field, a story in the wrong stage, a role that may not act, is a tool result with isError: true and a sentence that says what to do: "approve needs the owner role; ask the owner or use questions.ask". Roles are checked per action on the server, never per tool.

Search and discovery. The specification defines no search method, so search is a tool. It returns its hits as resource_link items, each a codeloop:// URI with a title and a one-line excerpt, and the agent reads the ones it wants. The same records are exposed as resources through URI templates, such as codeloop://story/{key}, codeloop://story/{key}/document/{name}, codeloop://wiki/{path} and codeloop://decision/{id}, listed by resources/templates/list, with story keys and wiki paths offered by completion. A client that shows a resource picker can browse the record without any tool call, and a client can subscribe to a story's resource to hear when it changes, which is how live presence reaches a board.

What the specification changes for this design. Version 2026-07-28 has no protocol sessions: every request carries its own credentials and client information. So the tool list may differ by the caller's role, a viewer's list leaves out actions it cannot take, and the server identifies the calling agent from the client information on each request and records it on the Agent entity. Tool annotations are hints a client must treat as untrusted, and they apply to a whole tool, not an action, so only search claims readOnlyHint, any tool with a delete action sets destructiveHint, and the server's role check is what actually protects the record.

Specification read on 17 October 2026, version 2026-07-28: tools, resources, completion, pagination, changes since 2025-11-25.

Registered and kept current by the agent itself; this record, not the credential, says which agent reported the work.

Story keys. A key is <prefix>-<number>: one to five letters, a hyphen, one to six digits, so three to twelve characters, unique within a project. The server that holds the record assigns the number, so two machines cannot hand out the same key: the hub for a local project, Codeloop Cloud for a linked one. Every write goes through that server, so a story has its key from the moment it is created.

Migration of old ids. Today's ids already have this shape, so c-321 becomes the key c-321 of a story with a new internal id. Import sets the project prefix to c and the counter past the highest number. Commit trailers, notes and wiki links keep working unchanged.

Agents. The agent entity keeps its version 1 shape. The session file becomes an agent in state working, the lease its files-held list, the computed holder the story's current agent; the stall check sets the state when last activity passes the limit. A person working by hand is an agent of kind person. Agent records sync on every change, so a team sees every machine's agents on one board, and the cloud marks an agent stalled when its machine stops reporting.

Reviews and approve with conditions

A review is an object on the story. A reviewer, a person or an agent, writes a review with a verdict and findings through the reviews tool. Each finding has a severity, a file and line, an owner and a status. Open findings are routed to the story's current agent and appear in its brief. A finding closes when a commit names the finding's id in a trailer and the server sees that commit; a member can also waive one with a note. This replaces the review files kept beside the story and the five-question cap, because findings are counted and closed one by one instead of read from a file.

Approve with conditions. At a gate with open questions, the agent's handed-back work carries a recommended answer for each. One owner action approves the gate and accepts those recommendations as the answers, recorded as the owner's. An owner who disagrees with one answers it first, then approves.

Local and cloud, the same server

The same server runs in two versions. With open source, the command line, the web board and agents talk to a local server, the hub on your machine, or one nearby on your network. With Codeloop Cloud they talk to a remote server hosted on Protobox; the same Cloud server can also be hosted on-prem, with Cloud's features. Linking a project adds sharing and takes nothing away. Neither version prescribes a process. Steps (lanes) stay configurable per team in both; in Cloud they are shared across the workspace together with its named agents.

What moves. On a linked project the command line, hooks and agents call the remote server for every read and write, so there is no second copy of the record to keep in step. Lanes, config and named agents are workspace records on that server, changed only by an owner. Activity streams, the record of which files and commands a coding session touched, stay on the machine. Code never moves.

Migrating an existing board. codeloop import reads today's shared board file and any export folder, creates the stories with new internal ids and their old keys, and says so. From then on the file is unused; the owner may delete it from git. Export is the reverse and complete: codeloop cloud disconnect followed by an export leaves a project that can be imported anywhere.

Identity, roles and credentials

Nobody signs up twice. A codeloop sign-up creates a Protobox account and a workspace behind it, and an existing Protobox user signs in with that account. Protobox already provides accounts with verified email, workspaces with members and invitations, roles, and API keys with a kind and a workspace or project scope. What it lacks is a way for a command line to sign in without a password prompt; that is the device flow below, new work on Protobox.

Four Protobox roles map onto three codeloop roles; owner and admin both decide, because splitting them has no use on a board. A reviewer and the person behind a builder agent are both members. There are no agent keys: an agent connects with its person's sign-in, the token codeloop login gives, sent as the bearer header, and acts with that person's role. The server checks the role on every call, no tool argument can raise it, and a refusal names the role that could have done it. The owner chose this for simplicity over per-agent attribution. The trade-off is that every action traces to the person, not to the agent, and an agent run by an owner can do what the owner can. The Agent entity still records which agent reported the work: an agent registers through the agents tool and reports as it goes, so the board and the history name it.

Delegated approvals. Each person keeps one sign-in. An owner can delegate approvals to a named orchestrator, an agent in the workspace's cast, and revoke that at any time. Every approval it makes is recorded on the event as "approved by <orchestrator> on behalf of <owner>", so the history shows both who decided and who allowed it.

Public publishing, later

An owner chooses per project to publish the board and wiki at a public URL, read-only, through a privacy filter: deny by default, nothing marked private, no agent records, no specs before their gate, no evidence files, no keys or members, and every served text passes a machine-path scan that withholds a matching line with a marker. Activity streams are never in the cloud at all.

Docs platforms such as Mintlify already run this shape. Worth borrowing: a per-page public flag that can also be set for a whole group, so publishing is explicit and inspectable; "hidden" kept separate from "private", because a hidden page is still reachable by URL, so concealment is never used as access control; a noindex marker on pages reachable but not meant to be found; a stable public URL per project, custom domain later. Where codeloop differs: Mintlify's pages are public unless protected, codeloop's are private unless an owner publishes, because a board carries unfinished work.

Steps

Eight steps, each usable on its own. Steps 1 to 3 are the day-one release: they replace today's shared board file, give agents the stories MCP and search, and add reviews, approve with conditions, priority and live presence, with nothing hosted. Sizes use the board's scale (S, M, L) with a rough calendar reading. The order follows dependencies and that cut: everything needs one writer and a stable story id, so the record moves first; the MCP and hooks need the server to be the only door; reviews, approve with conditions, priority and presence are what an owner running several agents uses every day, so they ship before anything hosted. Story documents in the store come next, then the cloud as a second store, identity once the cloud exists, the named-agent cast and the constitution on top of identity, and publishing last because it is read-only on top of all of it.

Risks and what stays out of scope

  • The hub will not start on some machine. The command shows the log and exits; doctor and export still read the store. Nothing writes around the server.
  • Protobox is down. A linked project refuses writes with "server not available" until it returns. Provisional offline writes are a later option.
  • A merge-rule bug misplaces a story. History is add-only and replay deterministic, so any story can be replayed and the difference shown.
  • Private text reaches the public view. Deny by default, activity never leaves the machine, the path scan withholds matches, and one test feeds the view a story built to leak.
  • codeloop releases become tied to Protobox deploys. The API and sync protocol are versioned; the command line refuses a server it does not understand.
  • Pressure to make the cloud do the work. The hosted API has no verb for merge, gate run, orchestrated run or builder start, so the line holds by construction.

Later, not version 2: soft locks on files. An agent would mark the files it is about to change so another agent waits. The design issue to solve then is a stale lock: agents forget to release, so every lock needs an expiry renewed by the agent's heartbeat, and a lock whose agent stopped reporting lapses on its own.

Out of scope here: Protobox internals beyond identity; the web board's visual redesign; running agents in the cloud, by design; a hook file for Codex; links between projects; live shared editing of a document.

Open questions

1. When a P1 arrives, what happens to a P2 a builder is working on?

Options: (a) park it automatically with a note after the builder's uncommitted work is handed back; (b) ask the owner first; (c) no pause, the P1 waits for a free slot. Recommendation: (b) now, moving to (a) once hand-back on pause exists.

2. Where should checks such as size budget and health measure by default?

Options: (a) the story's branch against main; (b) main itself; (c) the branch the agent is on. Recommendation: (c), right for a founder running several agents on one branch and for a team on one worktree per story; a project can set (a) or (b).

3. On a linked project, where do the guard hooks read the edit lease?

The hooks must answer without waiting on the network, but a linked project keeps no local copy of the record. Options: (a) the hub keeps only the leases of the stories its agents hold, refreshed on each answer from the remote server; (b) the hooks call the remote server and refuse the edit when it does not answer in time. Recommendation: (a). An edit should not stall on a slow network, and a lease is small and changes only when the plan does.
